# Передача контекста проекта AtolGenerator

Дата фиксации контекста: **28.07.2026**.

Этот документ объясняет не только устройство программы, но и мотивы решений.
Он рассчитан на нового разработчика или AI-агента, который может прочитать код,
но не видел историю обсуждений с владельцем.

## 1. Как появился проект

Изначальная задача была небольшой: бухгалтер присылает сообщение с номерами
заказов и суммами, а оператор должен быстро пробить фактические возвраты денег.
Программа разбирала текст и отправляла `sell_refund` в АТОЛ Online.

Дальше проект вырос в рабочее место для трёх разных процессов:

1. обычные возвраты покупателям через API;
2. чеки коррекции по реализациям из 1С;
3. исправление накопленных расхождений из рабочего файла Obsidian.

Позже появились отчёты АТОЛ и Такскома, поиск чеков по ФПД, служебные записки,
сопоставление фискальных данных и подготовка CSV для обработки 1С.

Главная опасность проекта - внешне похожие операции имеют разный юридический и
технический смысл. Нельзя выбирать `sell`, `sell_refund` или
`sell_correction` только по удобству API.

## 2. Роль программы

Программа помогает оператору подготовить, проверить и сопоставить данные.

Она **не пробивает обычные реализации вместо кассиров**. Кассиры делают это в
1С. Из AtolGenerator по реализациям формируются прежде всего:

- чек коррекции, если чек не был пробит;
- исправительная пара, если исходный чек ошибочен;
- в редком ручном режиме - обычный чек, когда владелец осознанно выбрал этот
  сценарий.

Прямая запись фискальных полей в документы 1С из программы не является основным
процессом. Результат готовится в CSV и загружается внешней обработкой 1С в
интерактивном сеансе пользователя.

## 3. Источники истины

| Данные | Источник |
|---|---|
| Документ, подразделение, сумма, номенклатура | 1С |
| Факт фискализации, ФД и ФПД | ОФД/Такском и карточка чека |
| UUID и история запросов API | журнал АТОЛ и `punched_checks.jsonl` |
| Очередь старых ошибок и пояснения | рабочий Markdown Obsidian |
| Формат API/XML | официальная документация и XSD АТОЛ |
| Реально реализованное поведение | код текущего коммита |

Если источники противоречат друг другу, нельзя молча выбирать удобный. Нужно
показать расхождение пользователю.

## 4. Сценарии чеков

### 4.1 Фактический возврат по заказу

Пример входа: сообщение бухгалтера с заказом, датой, суммой и иногда ФИО или
пометкой `(доставка)` / `(сборка)`.

- операция `sell_refund`;
- API АТОЛ;
- наличные или безналичные выбираются оператором;
- это реальное движение денег, поэтому тег 1192 не нужен;
- обычный товар использует ставку расчётной части для возврата;
- для услуги агент, поставщик и ставка определяются по услуге и подразделению;
- если ФИО отсутствует, его можно получить из контактного лица заказа в 1С.

Фраза "чек на возврат" должна переводить форму в `sell_refund`. Оставлять
операцию `sell` в таком случае опасно.

### 4.2 Обычная оплата

- операция `sell`;
- API;
- товарная позиция представляет аванс/платёж;
- агентская услуга должна передавать агента и поставщика;
- собственная услуга доставки по России идёт без агента.

### 4.3 Реализация без чека

- обычную реализацию уже создали в 1С;
- если чек не был пробит и дата прошла, нужен `sell_correction`;
- формируется XML для ручной загрузки;
- API заблокирован;
- для ФФД 1.05 табличная часть не обязательна;
- агент не передаётся;
- номенклатура и подразделение всё равно нужны для определения ставки НДС;
- если услуга или ставка не определены, эта строка пропускается с ошибкой, а
  остальные корректные строки продолжают формироваться;
- на каждый чек нужна служебная записка.

### 4.4 Ошибочный исходный чек

Если чек пробит неверной датой, суммой, оплатой, номенклатурой или по неверному
документу, формируется исправительная пара:

1. обратный обычный чек, отменяющий исходный, с тегом 1192 и ФП исходного чека;
2. правильный чек коррекции;
3. в XML ФФД 1.05 тег 1192 не добавляется в коррекцию из-за XSD; вместо него
   используются дата и номер основания в `correction_info`;
4. формирование только в XML;
5. одна служебная записка описывает оба чека.

Сумма, оплата и табличная часть второго чека могут отличаться от исходного.

### 4.5 Obsidian

Obsidian содержит очередь расхождений между 1С и ОФД с кратким пояснением:

- `[ ]` - работа не закрыта;
- `[x]` - чек исправлен, служебная записка проверена, пояснение внесено в 1С.

Из пояснения строится предварительный сценарий. Если он неоднозначен, программа
должна показать `Нужен сценарий`, а не угадывать.

Obsidian-сценарии передаются в отдельное окно исправлений. В этом окне только
генерация XML и DOCX, без кнопки API.

## 5. Услуги, агенты и НДС

Рабочие типы услуг:

- доставка;
- сборка.

Агент определяется сочетанием типа услуги и подразделения 1С. Правила хранятся
в настройках. При отсутствии правила чек не формируется.

Особое правило: у подразделения `Интернет-магазин (Продажи)` есть собственная
номенклатура `Услуга по доставке (Россия)`. Для неё нет агента и поставщика,
ставка относится к собственной услуге.

У разных агентов могут быть разные:

- ИНН и телефон;
- ставка НДС;
- юридический тип агента для реквизита АТОЛ.

Нельзя всем агентам без проверки назначать один юридический тип. Список
допустимых значений должен соответствовать официальному перечислению АТОЛ.

В проекте встречаются исторические чеки со ставками 20/120 и текущие требования
22/122, а у услуг - 5 или расчётная 5/105. Нельзя делать глобальную замену ставки
по одному отчёту. Выбор зависит от типа документа, момента расчёта, услуги и
переходного состояния 1С.

## 6. Отчёты и завершение процесса

После ручной загрузки XML в АТОЛ:

1. загружается журнал АТОЛ;
2. загружается отчёт ОФД/Такскома;
3. чеки сопоставляются по доступным идентификаторам;
4. готовится CSV;
5. внешняя обработка 1С заполняет фискальные поля или комментарий.

Для обычного чека коррекции в документ заносятся данные этого чека. Для
исправительной пары исходные ошибочные реквизиты документа не следует
перезаписывать как будто ошибки не было; сведения об отмене и правильном чеке
фиксируются в комментарии по согласованному формату.

Отчёт Такскома может быть ограничен фильтрами или числом строк. Отсутствие чека
в одном XLSX не доказывает отсутствие чека в ОФД. Для таких случаев существует
поиск в личном кабинете по ФПД через WebView2 и локальный накопительный кэш.

## 7. Ключевые модели и сервисы

### Основные модели

- `OrderEntry` - единица работы: заказ, документ или исправительный случай;
- `OrderItem` - строка чека;
- `ServiceProvider` - правило услуги, подразделения, агента, НДС;
- `OneCRealization` - данные реализации из 1С;
- `CheckData` - полностью рассчитанный чек перед XML;
- модели Obsidian - исходная строка, состояние, план и подтверждения.

### Основные цепочки

```text
сообщение -> OrderParserService -> OrderEntry
          -> OneCService (обогащение услуги)
          -> AtolApiService (только разрешённый API-сценарий)
```

```text
1С/Obsidian -> CorrectionTypeDetector
            -> CorrectionPlanService
            -> CorrectionWorkViewModel
            -> CorrectionGeneratorService
            -> XmlGeneratorService + DOCX
```

```text
АТОЛ CSV + ОФД XLSX + XML
            -> ReportImport/ReportReconciliation/XmlOfdMatcher
            -> CSV для внешней обработки 1С
```

## 9. Последний диагностированный инцидент

В партии из пяти возвратов:

- два обычных заказа успешно пробились;
- при повторном запуске они были отправлены повторно;
- перед правильными возвратами по ним также ушли ошибочные чеки `sell`, потому
  что текст сообщения не переключил тип операции;
- две услуги не дошли до АТОЛ из-за отсутствующих правил агента для
  подразделений;
- одна услуга дошла до АТОЛ и получила код 167
  `Невозможно записать реквизит агента`.

По итогам реализованы распознавание возврата, подтверждение операции, защита
от повторов, сохранение ошибочных строк в очереди и локальная проверка агента
до запроса токена. Список агентов и юртип сверены с владельцем (см. раздел 8);
окончательное подтверждение, что код 167 не повторится, будет только по факту
следующего реального пробития этой услуги.

Уже пробитые ошибочные/повторные чеки код исправить задним числом не может. Их
нужно отдельно сверить в ОФД и обработать как фискальное исправление.

Диагностические логи, переданные для этого случая, содержали строку подключения
1С с паролем. Их нельзя добавлять в репозиторий или пересылать без очистки.
Пароль следует сменить.

## 10. Как принимать следующие задачи

Для каждой новой задачи зафиксировать:

```text
Цель:
Что пользователь сделал:
Фактический результат:
Ожидаемый результат:
Тип операции: sell / sell_refund / sell_correction / исправительная пара
Канал: API или XML
Источник данных: сообщение / 1С / АТОЛ / ОФД / Obsidian
Пример файла или лога:
Ограничения:
Критерии готовности:
Нужен ли релиз:
```

Полный старый чат переносить не обязательно. Важнее приложить этот документ,
последний структурированный запрос, скриншоты/логи и явно указать незавершённые
решения.
