Этот файл является первой точкой входа для работы с проектом. Перед любыми
изменениями прочитай:

1. живую базу владельца `D:\Obsidian\Vaults\BASE LAPTO{\База знаний\AtolGenerator`

2. `docs/project-handoff.md` - история решений; раздел 8 может отставать от тега;
3. `docs/README.md` - индекс технической документации;
4. профильный документ из `docs/workflows/`;

## Назначение проекта

AtolGenerator - производственное Windows-приложение для кассовых операций ИП:

- фактические возвраты покупателям по сообщениям бухгалтера через API АТОЛ;
- подготовка XML чеков коррекции по реализациям из 1С;
- исправление ошибочных чеков из очереди Obsidian;
- поиск чеков и сверка журналов АТОЛ, ОФД/Такскома и данных 1С;
- формирование служебных записок и CSV для внешней обработки 1С.

Обычные реализации пробивают кассиры в 1С. AtolGenerator не должен превращаться
в замену этому процессу.

## Неприкосновенные правила

1. Обычный реальный возврат по заказу - `sell_refund` через API, без тега 1192.
2. Чеки `*_correction` загружаются только XML в кабинете АТОЛ. Обратный чек
   исправительной пары и полная отмена — обычный `receipt` через API. Смешивать
   возврат и коррекцию в одном XML нельзя.
3. Obsidian-исправления открываются в отдельном окне. Их нельзя помещать в
   обычную форму оплаты/возврата.
4. При исправительной паре тег 1192 с ФП исходного чека передаётся в чеке
   обратной операции. Второй документ является чеком коррекции и использует
   `correction_info`, поскольку XSD ФФД 1.05 не допускает в нём тег 1192.
5. Для `sell_correction` по ФФД 1.05 табличная часть не обязательна. Агент в
   такой чек не передаётся, но номенклатура и подразделение нужны для выбора НДС.
6. Если услуга, агент, ставка НДС, операция или исходный чек не определены
   однозначно, чек не формировать. Показать ошибку и продолжить обработку
   остальных корректных строк.
7. Агента нельзя угадывать. Он определяется по типу услуги и подразделению 1С
   либо задаётся владельцем в настройках.
8. Фискальная отправка необратима. Перед изменениями API-сценария изучить
   журнал и получить подтверждение ожидаемой операции.
9. Не логировать пароли, токены, cookies и полные строки подключения.
10. Не коммитить runtime-файлы, отчёты, Obsidian пользователя и персональные
    данные. Смотри `docs/security.md`.

## Технический стек

- WPF, .NET 8, Windows;
- MVVM;
- АТОЛ Online API v4 и ручная XML-загрузка;
- 1С УТ 10.3 через `V83.COMConnector`;
- WebView2 для личного кабинета Такском;
- ClosedXML/Open XML для отчётов;
- DOCX для служебных записок.

## Рабочий порядок для изменения

1. Сначала воспроизвести проблему по коду, логу и приложенному файлу.
2. Отделить бизнес-ошибку данных от технического дефекта.
3. При неясной фискальной семантике задать владельцу конкретный вопрос.
4. Вносить узкие изменения в существующую архитектуру.
5. Проверить Debug-сборку, x64 и x86 publish, `git diff --check`.
6. Для XML проверить операцию, оплату, НДС, агента, поставщика и тег 1192.
7. Не выполнять реальный запрос АТОЛ в тестах.
8. Перед коммитом показать итог и незакрытые риски.

## Версии

Текущая версия исходного кода: `v2.3.6`. Версии увеличиваются последовательно.
Переход на `v3` делает только владелец проекта.

Версия в теге и все четыре поля версии в `AtolGenerator.csproj` должны
совпадать. Релиз должен содержать self-contained ZIP для x64 и x86: exe и
`WebView2Loader.dll` соответствующей архитектуры.

## Общение с владельцем

- язык общения и интерфейса - русский;
- не маскировать неопределённость уверенным предположением;
- для фискальных сценариев лучше один точный уточняющий вопрос, чем неверный чек;
- после исправления кратко объяснить причину, что изменено и как проверить;
- не удалять рабочие режимы как "редко используемые" без прямого разрешения.
